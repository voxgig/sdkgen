      (1) The no-test test-client sentences (d48de033ea, 9577ba159e) are false for ts. Without the test feature, ts `test()` reaches `config.makeFeature('test')`, and that function has no fallback: `new FEATURE_CLASS['test']()` runs on undefined and throws, so no client is returned. go, c, py and rust fall back to the base feature, so the sentences are true for them.
      
      (2) "An action returns that action's OWN response" (cf564b5fca) contradicts the design that every entity operation returns the entity. An action is a `create` call, and `create` returns `this` with the response stored as its data.
      
      The design weaknesses I found:
      - **The mask hides shared prose words, not just language tokens.** "record", "utility", "id" and "fields" are masked as entity or field slots because the baseline model has entities named record and utility and fields named id and fields. The literal `data` (a key of the direct result) is masked as the accessor parameter, `err` (also a result key) as errVar, and the shared word "array" as ts's collection fact. Wrong wording in any of those places would match a reference sentence.
      - **Some shared sentences are split into several "single-language" sentences.** The mask leaves printer output unmasked (the `r.read` expression, `Direct()`/`sdk_direct()`, the `Control options (e.g. ...)` example). So "A failed request is reported in the result ..." shows up once per language.
      - **The direct() return sentence names a hard-coded `err` (ReadmeRef.ts:211).** That misleads in go and c. Their signatures carry an error variable or out-parameter that direct() never sets; the failure is in the result map's "err" key.
      - **c's prose says to branch on `getp(result, "ok")`.** That is a pointer, so the test is always true when the key is present. c's own README example branches on `voxgig_as_bool(getp(result, "ok"))`.
      
      The open question: the heading "Instance Functions" should be "Client Functions" for c, clojure and elixir.
