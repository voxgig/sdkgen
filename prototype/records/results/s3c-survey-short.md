# Survey, short form: one line per runtime and question

The first sentences of each answer, to find your way. The answers in full, with file, line and the quoted line, are in `P/results/s3c-survey.md` under the same question and language. Every line is one reader's claim.


## 1. The accessor and the cache

- **ts** (read and certain): The accessor makes a new entity on every call, with or without an argument, including undefined or null. It never caches. The argument is the entity OPTIONS object (entopts), not initial data. null or undefined becomes {} in the entity constructor.
- **js** (read and certain): Same as ts: a new entity on every call, never cached. The argument is entopts, not data. null or undefined becomes {}.
- **go** (read and certain): A new entity every call, with or without an argument: the client keeps no entity. The argument (named `data`) is NOT data: it is passed through as the entity's entopts (entity options), so `client.Planet(map[string]any{"id":"x"})` sets no data.
- **c** (read and certain): A new entity every call (calloc in entity_new); the client keeps none. The argument is the entity options (`entopts`, a voxgig_value* map; NULL or a non-map gives a fresh map with active=true). It does not set data.
- **py** (read and certain): The accessor makes a new entity on every call, with or without an argument. The client keeps no cache. The argument is NOT data: it is passed as the entity constructor's second parameter, `entopts`, so it becomes entity options.
- **rb** (read and certain): The accessor makes a new entity on every call (`Cls.new(self, data)`), with or without an argument. The client keeps no cache.
- **php** (read and certain): Called with no argument or null, the accessor returns one entity that the client keeps in a private field and creates on the first call. Called with a non-null argument, it makes a new entity every time. The argument becomes the entity's entopts, not its data.
- **perl** (read and certain): The accessor makes a new entity on every call, with or without an argument; there is no cache. The argument is passed to the entity constructor as entopts, not as data.
- **lua** (read and certain): With no argument (nil) the accessor returns one entity the client keeps: the first call makes it and stores it on the client, and later calls return that same instance, state included. With an argument it makes a new entity every time and does not cache it.
- **elixir** (read and certain): No cache: the accessor is a module function that calls the entity module's new/2 on every call, with or without entopts, so each call returns a new entity node.
- **java** (read and certain): The accessor (e.g. client.planet(entopts)) makes a new entity on every call, with null or with a map. There is no cache field and no no-argument overload; null is the 'no argument' form.
- **kotlin** (read and certain): Same as java: client.planet(entopts) constructs a new entity every call, null or a map. No cache, no zero-arg overload.
- **scala** (read and certain): The accessor makes a new entity on every call, whether it gets null or a map. The client keeps no cache. The argument is the entopts map. It is passed by reference and mutated: the entity writes an `active` key into the caller's map.
- **csharp** (read and certain): The accessor makes a new entity on every call, with no argument (`entopts = null` is the default), with null, or with a dictionary. The client keeps no cache. The dictionary is passed by reference and mutated: an `active` key is set in the caller's map.
- **swift** (read and certain): A new entity every call, with or without an argument (nil or a VMap). The accessor builds a fresh entity instance each time and the client keeps no cache.
- **cpp** (read and certain): A new entity every call, with or without an argument (Value::undef() or a map). The accessor returns std::make_shared of the entity class each time, and the client holds no entity cache.
- **zig** (read and certain): Same as rust: the accessor takes a required `entopts: Value` and always calls `.new`, so every call returns a newly allocated entity. `h.vnull()` and a map behave the same here, except that a map is used as the entity options.
- **rust** (read and certain): The accessor takes a required `entopts: Value` and always constructs a new entity; the client keeps no entity cache. Passing `Value::Noval` (the null) or a map makes no difference to this: a non-map entopts becomes an empty map, and a new `Rc<Entity>` comes ba …
- **clojure** (read and certain): No cache. The accessor `(api/<name> client x)` calls `make`, which calls `new-entity`. Every call returns a new entity map, whether x is nil or a value.
- **ocaml** (read and certain): No cache. `Sdk_client.<name> client entopts` calls `<Mod>.make client entopts`, which builds a new `entity_obj` record on every call, with Noval or with a value.

## 2. Getters: a copy or the live value

- **ts** (read and certain): options() returns struct.clone(_options). That is a deep JSON copy of plain data, but functions (system.fetch) and class instances (extend features) are shared by reference.
- **js** (read and certain): Identical to ts: options() is a deep copy of plain data; utility() returns the live Utility instance, because clone keeps class instances by reference; data() and match() are deep copies; entopts() is a merged copy; client() is live.
- **go** (read and certain): Client options getter `OptionsMap()`: deep clone. Client utility getter `GetUtility()`: a copy (new *Utility struct, value-copied, its Custom map copied one level; function fields shared). Entity data getter `Data()`: clone. Match getter `Match()`: clone.
- **c** (read and certain): Options getter `sdk_options_map(client)`: deep clone. Utility getter `sdk_get_utility(client)`: a newly allocated Utility sharing the same fetcher pointer with a shallow copy of the custom map (a copy, not the live struct). Entity `vt->data(e, NULL)`: clone.
- **py** (read and certain): Options: `client.options` is a property that returns the live dict the client holds, and it has a setter. `client.options_map()` returns a deep clone.
- **rb** (read and certain): Options: `client.options` is an attr_accessor that returns, and allows replacing, the live Hash. `client.options_map` returns a deep clone.
- **php** (read and certain): options_map() returns a deep clone. get_utility() returns a new utility object (UtilityType::copy) that holds the same closures, so it is a shallow copy. data_get() and match_get() each return a clone.
- **perl** (read and certain): options_map returns a deep clone. get_utility returns a new utility hash with the same coderefs and a copied custom map, so it is a shallow copy. data_get and match_get each return a clone. There is no entity-options getter and no client getter.
- **lua** (read and certain): options_map() returns a deep clone. get_utility() returns a new Utility table holding the same function members and a shallow copy of custom, so it is a copy but the functions are shared. data_get() and match_get() return clones.
- **elixir** (read and certain): options_map(client) returns a clone. get_utility(client) returns the live utility node the client holds, with no copy. This is a difference from lua. data_get(ent) and match_get(ent) return clones.
- **java** (read and certain): optionsMap(): deep clone. getUtility(): a new Utility holder whose function members are the same references (shallow copy; only the custom map is copied). data(): clone. match(): clone. No entity-options getter exists (entopts is a protected field).
- **kotlin** (read and certain): Same as java: optionsMap() deep clone; getUtility() new Utility with shared function references (custom map copied); data() clone; match() clone; no entity-options getter (entopts protected var).
- **scala** (read and certain): `optionsMap()` returns a deep clone. `getUtility()` returns `Utility.copy()`: a new Utility with the same function references and a fresh copy of the `custom` map. `data()` returns a clone. `matchArgs()` returns a clone.
- **csharp** (read and certain): `OptionsMap()` returns a deep clone (StructUtils.Clone). `GetUtility()` returns `Utility.Copy(_utility)`: a new Utility with the same delegates and a fresh copy of `Custom`. `Data()` returns a clone. `Match()` returns a clone.
- **swift** (read and certain): The options getter optionsMap() returns a deep clone. The utility getter getUtility() returns a new Utility whose function slots are copied from the original, a shallow copy. The data getter data() returns a clone.
- **cpp** (read and certain): The options getter optionsMap() returns Struct::clone(options). The utility getter getUtility() returns utility->copy(), a new Utility with its function slots copied. The data getter data() returns a clone. The match getter match() returns a clone.
- **zig** (read and certain): Client options: `options_map()` returns `h.clone`, a deep clone. Client utility: `get_utility()` returns `Utility.copy`, a new Utility with the same fetcher and a shallow copy of `custom`.
- **rust** (read and certain): Client options: `options_map()` returns a deep clone. Client utility: `get_utility()` returns `Utility::copy`, a new Utility whose fetcher is the same shared Rc and whose `custom` map is a shallow copy (a new map holding the same values), so it is a shallow co …
- **clojure** (read and certain): Clients: `options-map` returns a deep clone. `get-utility` returns a NEW atom holding the same map of functions, with only `:custom` cloned (a shallow copy). It exists only in `sdk.client`, not in the public `sdk.api`.
- **ocaml** (read and certain): Sdk_client has no options getter and no utility getter. The client's `cl_options` and `cl_utility` are mutable record fields that hold the live values. `Sdk_helpers.client_options_map client` is a public helper that returns a clone.

## 3. The stream and a signal

- **ts** (read and certain): Yes. stream(action, args, callopts) copies callopts.signal into ctrl.signal. It is an AbortSignal (Control types it that way). It is checked before each item is yielded, and the generator returns quietly once it has aborted.
- **js** (read and certain): Same as ts: callopts.signal (an AbortSignal) is copied to ctrl.signal. Each yield is checked and the stream returns quietly on abort. The fetch is aborted, and the resulting error is swallowed when the signal has aborted.
- **go** (read and certain): Yes. `Stream` reads `callopts["signal"]`, accepted as a channel (`<-chan struct{}` or `chan struct{}`; anything else is ignored).
- **c** (read and certain): No signal. `<entity>_stream` reads only `ctrl` and `body` from callopts (callopts is also copied into ctrl as `stream`); there is no signal or cancellation key.
- **py** (read and certain): Yes. `stream` reads `callopts["signal"]`. It accepts either a callable, whose truthy return means aborted, or any object with an `aborted` attribute, such as an event-like flag. The signal is checked only before each item is handed over.
- **rb** (read and certain): Yes. `stream` reads `callopts["signal"]`, a value that responds to `call`, such as a lambda or Proc, or that responds to `aborted`. It is checked before each item.
- **php** (read and certain): Yes. stream reads callopts['signal']. It may be a callable that returns true to abort, or an object with an `aborted` property. It is checked before each yield, and when it is set the generator returns and ends quietly, with no error.
- **perl** (read and certain): Yes. stream reads callopts->{signal}, and only a coderef counts: when it returns true, the iterator returns undef, which is the same as exhaustion. An object with an aborted flag is ignored, which PHP does accept. The signal is checked on each pull.
- **lua** (read and certain): Yes. stream reads callopts["signal"]. The signal can be a function (it aborts when the call returns a truthy value) or a table with an `aborted` field. It is checked before each item is yielded.
- **elixir** (read and certain): Yes. stream reads callopts "signal", which must be a 0-arity function. It counts as fired only when it returns exactly true.
- **java** (read and certain): Yes: stream(action, args, callopts) reads callopts.get("signal") and uses it only if it is a java.util.function.BooleanSupplier (true = aborted); anything else is ignored.
- **kotlin** (read and certain): Yes: callopts["signal"] is used only if it is a Kotlin Function0 (a () -> Boolean); the stream checks it before each item and stops (sequence ends) when it returns true. Differs from java in the type: Function0 vs BooleanSupplier.
- **scala** (read and certain): Yes. `stream` reads `callopts.get("signal")`. It must be a Scala `Function0` (`() => Boolean`); any other type is ignored and treated as never aborted. The check runs in `hasNext` before each pull.
- **csharp** (read and certain): Yes. `Stream` reads `callopts["signal"]` as a `System.Threading.CancellationToken`; any other type becomes CancellationToken.None. It also takes a second token through `[EnumeratorCancellation] CancellationToken cancel`, which `WithCancellation` passes.
- **swift** (read and inferred): Yes. stream reads callopts["signal"] as a native `@Sendable () -> Bool` function that returns true once the caller has aborted. When it returns true, the yield loop breaks and the stream finishes early, with no error.
- **cpp** (read and certain): No. stream reads only `ctrl` and `body` from callopts and copies callopts into ctrl.stream. It reads no signal, and the runtime has no signal type.
- **zig** (read and certain): No. `stream` reads only `ctrl` and `body` from callopts, and puts callopts into `ctrl.stream`. No signal is read anywhere, so nothing can fire.
- **rust** (read and certain): No. `stream` reads only `ctrl` and `body` from callopts. The whole callopts map is also copied into `ctrl.stream`, but nothing reads a signal from it. Neither the runtime nor the streaming feature has a signal, abort or cancel concept.
- **clojure** (read and certain): Yes. `stream` reads `"signal"` from callopts. It is a 0-arg function, not an abort object. The lazy sequence calls it before each element is yielded.
- **ocaml** (read and certain): Yes. `e_stream` reads `signal` from callopts. It must be a struct `Func` value (for example `vfunc0 (fun () -> Bool true)`). It is called before each Seq node is produced, and when it returns `Bool true` the Seq ends with `Seq.Nil`. There is no error.

## 4. Cancelling an operation

- **ts** (read and certain): Yes. Pass an AbortSignal as ctrl.signal: load(match, { signal }), list(match, { signal }), or direct({ ..., ctrl: { signal } }). makeFetchDef hands the signal to fetch. A signal that has already aborted throws before sending, so nothing is sent.
- **js** (read and certain): Same as ts: ctrl.signal (an AbortSignal) cancels load, list and direct. An operation rejects with an error whose code is 'request_aborted' and whose cause is the signal's reason. direct returns { ok: false, err } with that error.
- **go** (read and certain): No. Load/List/Direct take no context.Context and no cancel signal; ctrl has no cancellation key (Control holds Throw, Err, Explain, Actor, Paging); the default transport builds the request with http.NewRequest (no context). Not found anywhere in core/utility.
- **c** (read and certain): No. load/list/direct take (reqmatch/fetchargs, ctrl, PNError**); Control has no cancel field, and the built-in HTTP transport has only a fixed 30 s deadline (HTTP_TIMEOUT_MS), not caller cancellation.
- **py** (read and certain): No. A caller cannot cancel `load`, `list` or `direct` once it has started. The control object has no signal, token or context: ctrl carries only throw_err/throw, explain, actor and paging.
- **rb** (read and certain): No. `load`, `list` and `direct` have no caller cancellation: the Control class carries only throw_err, err, explain, actor and paging. A timeout is possible only through the timeout feature in the client options.
- **php** (read and inferred): No. ctrl for load, list and direct carries throw, explain, actor and paging, and nothing that cancels. The transport is synchronous (cURL or file_get_contents). The timeout feature says outright that an in-flight request cannot be aborted.
- **perl** (read and inferred): No. ctrl carries throw, explain, actor and paging only. Transport is a blocking HTTP::Tiny request, and the runtime has no signal, token or context.
- **lua** (read and certain): No. ctrl has no signal, token or context, and direct has none either. Transports are synchronous. The timeout feature only discards a late result after the call finishes.
- **elixir** (read and certain): No. The control node holds only throw_err, err, explain, actor and paging. No cancellation path exists for ops or direct. The timeout feature only adds a `timeout` key to fetchdef and turns a late response into a timeout error.
- **java** (read and certain): No cancellation API: Control has no signal/token field and ctrl is read only for throw, explain, actor, paging. load/list/direct run synchronously on the caller's thread.
- **kotlin** (read and certain): No cancellation API, same as java (no signal in Control/ctrl; synchronous). Thread interruption would surface as RuntimeException "fetch: ..." (inferred).
- **scala** (read and inferred): No. Control has no signal, token or context field, and the context parser reads only throw, explain, actor and paging from ctrl. The default transport calls the blocking `HttpClient.send` with nothing that can cancel it.
- **csharp** (read and certain): No. Load, List and Direct take no CancellationToken. Control has no token field, and the context parses only throw, explain, actor and paging. The default transport makes a synchronous `HttpClient.Send(req, ...)` with no token.
- **swift** (read and certain): No. load, list and direct take no signal, token or context. Control holds only throwErr, err, explain, actor, paging and streamOut, and the context reads only throw, explain, actor and paging from a ctrl map.
- **cpp** (read and certain): No. Control has throwing, err, explain, actor and paging, and nothing else. No operation, list or direct takes a token, and there is no cancellation path anywhere in core or the pipeline.
- **zig** (read and certain): No. The Control struct and the context ctrl parsing cover throw, explain, actor and paging only, and the runtime is synchronous. There is no cancellation.
- **rust** (read and certain): No. The runtime is synchronous, and Control holds only throw, err, explain, actor and paging. The context reads only throw, explain, actor and paging from ctrl. There is no signal, token or context to cancel load, list or direct once started.
- **clojure** (read and inferred): No cancellation option exists. The control record holds throw/err/explain/actor/paging only, and nothing reads a signal from ctrl. The default transport blocks in `HttpClient.send`.
- **ocaml** (read and certain): No. The control record carries only throw, err, explain, actor and paging, and nothing in the runtime reads a signal from ctrl. A started load, list or direct cannot be cancelled by the caller.

- **js** (read and certain): Same as ts: async generator. The operation runs on the first iteration step, not at the call.
- **go** (read and certain): Beside the caller, in a goroutine started at the call. Stream makes an unbuffered channel, builds the context, starts `go func()` and returns the channel at once; the goroutine runs all pipeline steps (request included) immediately, whether or not anyone reads …
- **c** (read and certain): At the call, synchronously, before it returns: the stream function runs every pipeline step and returns a whole List (or the streaming feature's producer output, also obtained before return); the caller then walks the list. No thread.
- **py** (read and certain): The operation runs when the caller first asks for an item. `stream` contains `yield`, so it is a generator function and nothing in its body runs at the call, not even building ctx.
- **rb** (read and certain): The work is split. At the call, lines 105-135 run eagerly: the context is built and the body is attached. Then `Enumerator.new` (line 140) is returned without running the pipeline.
- **php** (read and certain): When the caller first asks for an item. stream is a PHP generator function (it returns \Generator and contains yield), so none of its body runs until the first iteration. That includes make_context and the pipeline in _stream_steps.
- **perl** (read and certain): At the call, eagerly. stream builds the context, runs the whole pipeline through _run_op, and only then returns an iterator coderef. Pipeline errors therefore die from stream() itself.
- **lua** (read and certain): When the caller first asks for an item. stream builds the context, wraps the pipeline in a coroutine that has not started, and returns an iterator. The first iterator call resumes the coroutine, which runs the pipeline steps and then yields items.
- **elixir** (read and certain): At the call. stream/4 runs Pipeline.run_op synchronously before it returns. With the streaming feature it also calls the feature's stream function then, and that function builds its items eagerly as a list. Only the take_while/map/guard wrapping is lazy.
- **java** (read and certain): At the call. stream() runs the whole pipeline (runOp) synchronously, and also obtains the streaming feature's iterator, before it returns the java.util.stream.Stream; only pulling items from that iterator is deferred to consumption. No thread.
- **kotlin** (read and certain): At the call, as java: runOp and the streaming-source get() run before the lazy Sequence is returned; items are pulled from the source as the caller iterates. No coroutine/thread.
- **scala** (read and certain): At the call. `stream` builds the context and runs `runOp` (the whole request) synchronously, then builds and returns the Iterator. Iterating only reads results that already exist, or the streaming feature's iterator if that feature is active.
- **csharp** (read and inferred): When the caller first asks for an item. `Stream` is an async iterator (`async IAsyncEnumerable` with `yield`), so nothing in its body runs at the call.
- **swift** (read and certain): At the call, synchronously, before stream returns. The order is: (1) the full pipeline runs via runOp; (2) the items are read in full, from the streaming feature's result.stream closure (which returns an array) or else from the materialised result; (3) an Asyn …
- **cpp** (read and certain): At the call, synchronously. stream runs the pipeline stages inline (PrePoint through PreDone). If the streaming feature set result->stream, it calls that function and returns its vector. Otherwise it calls done() and returns the items as a std::vector<Value>.
- **zig** (read and certain): At the call. `stream` runs the whole pipeline in order. It then calls the streaming producer `sf.call(sf.ctx)`, which returns a `[]Value` slice, or else runs `done`. It returns `StreamResult{ .ok = slice }`. Nothing is lazy, and there is no thread.
- **rust** (read and certain): At the call, before `stream` returns. The whole pipeline runs synchronously inside `stream`: point, spec, request, response, result. Then, if the streaming feature attached a producer, `sf()` is called immediately.
- **clojure** (read and certain): At the call. `stream` runs the whole pipeline with `run-op`, then turns the result into a vector before it returns. That vector is built eagerly with mapv/vec, so a streaming feature's thunk is fully drained too. Only the signal check is lazy.
- **ocaml** (read and certain): At the call. `e_stream` runs `run_op` and then computes the whole item list before returning the Seq: it calls the feature's `rt_stream fn ()`, or reads resdata. The Seq only gates each element on the signal. There is no thread or domain.
